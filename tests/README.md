# guard — набор проверок по чек-листу L1

Проверяем, что каждая заявленная защита guard действительно работает, по той же
логике, что и аудит шлюза: легальное проходит, запрещённое блокируется,
маскируемое маскируется. В заголовке каждого теста — строка нашего чек-листа.

## Как запустить

Внутри того же контейнера, где собирается guard:

```bash
go build -buildvcs=false -o guard ./cmd/guard
apt-get update && apt-get install -y python3-pytest   # один раз
python3 -m pytest -v tests/
```

Ожидается: **22 passed, 2 xfailed**. Два xfail — это заявленный предел
regex-фильтра (обфускация), тест есть и ожидаемо не проходит.

## Что сюда НЕ вошло и почему

Проверки прокси и песочницы (egress-allowlist **K-02/K-03**, фильтр ответа
модели **L-03/H-03**, лимиты, запреты запуска) требуют рабочего backend'а
песочницы. На Linux это `bubblewrap` и, как правило, привилегированный
контейнер; авторы сами помечают Linux-backend как экспериментальный. В
обычном `podman` без `--privileged` они не запустятся.

Для этой части есть готовое в самом репозитории:

- `attack/run_attacks.sh` — 9 групп атак изнутри песочницы (FS, секреты, сеть,
  окружение, запуск программ), итог `pass/fail`;
- `attack/filter_test.sh` — фильтр запроса и ответа с локальной «моделью».

Запускать их лучше на macOS, где backend основной.

Корпус обходов для A-09/C-15 стоит гонять внешними инструментами (Garak,
promptfoo), а не расширять руками.
